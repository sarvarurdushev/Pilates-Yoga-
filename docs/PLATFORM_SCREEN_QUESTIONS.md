Source audit: 5 October 2026. This document compares the current rendered templates and their data sources with the later client-workspace request's section 33. It owns no acceptance status in `CURRENT_SPEC_ACCEPTANCE.md`. Template inspection establishes where an answer is rendered; browser assertions verify the named source and unavailable branches. These checks do not claim a measured human response time.

## Exact questions from the request

Section 33 says: “For every important screen ask: Can a user answer within 5-10 seconds:”

1. **WHO is this about?**
2. **WHICH SESSION is this?**
3. **WHAT exercise was performed?**
4. **WHICH camera angle was used?**
5. **WHAT was measured?**
6. **WHAT does the number mean?**
7. **WHAT changed?**
8. **WHAT does the coach think?**
9. **WHICH body region is involved?**
10. **WHAT should happen next?**

The section ends: “If any of those are unclear, the screen is not finished.” The 5–10-second expectation is a clarity requirement. It does not prescribe recruiting participants, a formal human study, or a test of every role × viewport × camera × metric combination. An operational inventory does not become clearer by inventing an exercise or clinical measurement. Its scope must instead be clear, and non-applicable questions must stay distinguishable from missing recorded data.

## How to read the matrix

- **D**: rendered by default in the current template. This is source evidence, not a new screenshot or browser assertion.
- **L**: available through a named link, tab or disclosure; the initial summary itself does not answer it.
- **U**: an explicit unavailable/not-recorded/no-comparable-value state, which is an honest answer when the underlying record lacks the fact.
- **N/A**: outside this screen's stated purpose. This is not a substitute for an answer on a measurement report.
- **G**: a concrete mismatch or missing contextual answer identified in source. Minimal fixes are listed below.

“Default” means the visible template rather than a collapsed technical section. A long default template may still require scrolling; only the cited browser checks below establish actual rendered visibility for their checked paths. A named route to the exact source is credited as **L**, rather than silently treated as a first-screen answer.

## Corrections and observed answer locations · 5 October

All six source-context omissions identified by the initial audit were corrected:

1. Client overview now labels its capture card **Latest assessment / Your latest assessment**. In a disposable Coach/Student organization, a newly saved practice newer than the capture left this truthful label and exact assessment link intact.
2. The visit's **At this visit → What happened** summary now names logged movements from the saved applicable program snapshot, followed by the remaining count. The browser asserted the exact saved movement name and one logged entry; unit cases cover unavailable historical names without inventing them.
3. The body region's source summary independently names the saved **protocol and camera view**. The browser opened Sarah's right-wrist region from a Shoulder flexion source lacking a supported wrist trend and still found the exact protocol and Front view.
4. Selected imaging detail shows **Capture date / Date not recorded** separately from the exact **Source visit · date** link. The browser uploaded an explicitly artificial PNG, saved an exact visit/analysis relation, checked the recorded date, cleared it, then verified the unavailable date after reload.
5. Program and body-map assigned movement copy prioritizes the Coach's saved **why_assigned** over generic exercise purpose. The full program and target-selection browser checks cover this source preference; unit tests use deliberately different rationale and purpose.
6. Client Program's **Latest revision → Read latest change** points to immutable history. The existing saved-version browser check shows the reason, actor, exact source visit and conservative adjacent-version differences without inferring that a changed dose caused improvement.

The same summary browser check saved new human feedback on a demo capture and found **COACH-WRITTEN FEEDBACK** in both Coach and Student reports, rather than using the capture's demo flag as the note's source. At **540px**, the saved visit summary still named its movement and had no horizontal overflow. It completed with **zero page errors** (`web/test/platform-summary.browser.mjs`, `/tmp/motion-summary-browser-1005.log`). This test intentionally excluded the atlas renderer; actual WebGL selection and feedback markers have separate acceptance receipts.

The matrix's other important families retain the actual three-role journey and integrated browser evidence listed above: Admin operational totals/relationships, role-specific client summaries, accepted/refused/identity-pending reports, same-protocol progress, body history and Student assigned practice. Where a screen has no performed exercise or camera capture (operations, plan prescription or scan review), its purpose is explicit and those questions are N/A. Unknown evidence and source-load failures remain visible unavailable answers, with named next actions. The current chart audit additionally records observed report traces, coordinate units/missing depth, comparison, progress, body and program chart branches.
