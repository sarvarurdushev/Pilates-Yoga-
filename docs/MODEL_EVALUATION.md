# Model decision and Hugging Face review

Reviewed 15 September 2026. This is an engineering evaluation for this application, not a leaderboard. Keep RTMO for class detection. Add a conservative, optional MediaPipe world-landmark display. Do not replace either with a mesh merely because it renders attractively.

## What was actually run

CPU: Intel Core i7-1165G7, 4 cores / 8 logical CPUs, no CUDA GPU available. Python 3.12, ONNX Runtime CPU with 4 intra-op threads. Runs were single local trials, sometimes alongside tests; timings are indicative, not throughput guarantees. No synchronized motion capture, calibrated cameras or human-annotated keypoint ground truth was available, so these measurements establish cost and failure behavior, not anatomical accuracy.

| Candidate | Local experiment | Observed time | Decision |
|---|---|---|---|
| Existing RTMO-m, 640 input | OpenCV basketball, skier, Messi; MediaPipe Warrior; then full visual corpus | Initial image inference roughly 0.23–0.33 s/frame. Final warm end-to-end photos roughly 0.20–0.36 s for single subjects, with optional 3D when accepted | Keep one-stage multi-person detector, tiling and downstream tracker |
| ViTPose Base Simple quantized ONNX | Downloaded ~84 MB from Hugging Face; ran on RTMO boxes for those four images | ~0.202–0.207 s for one person; 0.411 s for two, excluding RTMO detection | No demonstrated accuracy gain. A per-person refinement adds cost to the retained detector |
| MediaPipe Pose Landmarker Full | Downloaded official task asset; independently inferred image and world joints per RTMO crop | Initial call/model load ~0.46 s; subsequent initial benchmark calls ~0.03 s/person | Integrate as optional learned skeleton, gated by visible image-space agreement |

The final 1/5/10/20-person composites produced exactly 1/5/10/20 accepted bodies; representative end-to-end times were 0.35/0.57/0.72/1.49 s. These repeat the same photograph with no real occlusion. They do not predict GPU performance, tracking quality in a real class, or latency for 20 distinct articulated bodies. A crowded street clip had churn 2.0 and was refused for per-person movement reporting.

The original 3D benchmark's median RTMO–MediaPipe difference ranged around 0.02–0.06 torso lengths on its accepted examples. That is agreement between models, not distance to ground truth. The integrated version additionally checks all mutually confident visible joints and refuses excessive disagreement; at least six core body joints must agree. Segmentation is disabled because reading segmentation masks caused a reproducible native crash in this environment. No silhouette confirmation is claimed.

## Serious alternatives

The deployment-risk column below contains engineering judgments; models not run locally have no measured application accuracy or hardware minimum here.

| Model / representation | Scaling and temporal behavior | Deployment judgment and license |
|---|---|---|
| [ViTPose Base Simple](https://huggingface.co/usyd-community/vitpose-base-simple), 2D | Top-down person crops require detection; cost grows with people. Image model has no intrinsic identity or temporal smoothing | Useful potential refinement for difficult crops. Cannot recover detail absent in a distant/wide view and cannot prove occluded joints are visible. HF upstream card lists Apache-2.0. The tested [ONNX export](https://huggingface.co/onnx-community/vitpose-base-simple) needs upstream provenance retained. The family-wide AP headline is not an accuracy result for this quantized base model or Pilates footage |
| [MediaPipe Pose Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker), 33 image/world joints | CPU practical; video modes exist, but this integration deliberately uses independent single-image crops and does not claim 3D video tracking | Optional learned depth/scale. Inverted, occluded, rear and strongly foreshortened bodies need inspection. Agreement with 2D does not validate hidden depth. Framework code is [Apache-2.0](https://github.com/google-ai-edge/mediapipe/blob/master/LICENSE); retain applicable model notices |
| [SAM 3D Body](https://github.com/facebookresearch/sam-3d-body), MHR mesh | Promptable single-image mesh; per-person crops/prompts still need association. Not a temporal tracker | Strong next GPU experiment for unusual poses and occlusions, subject to actual camera evaluation. Not run: no CUDA GPU or approved gated model access. [HF checkpoint](https://huggingface.co/facebook/sam-3d-body-dinov3) requires contact sharing/access conditions and uses SAM licensing. No terms were accepted on the user's behalf |
| [Multi-HMR](https://github.com/naver/multi-hmr), SMPL-X / newer Anny option | Single-shot multiple camera-space meshes. Official runtimes 29–126 ms for listed variants were measured on a V100-32GB, not this CPU; no temporal identity guarantee | Interesting class architecture; local CPU performance unknown. Camera intrinsics/distortion and small-body detail still matter. February 2026 Anny checkpoint noted. The repository's current [license](https://raw.githubusercontent.com/naver/multi-hmr/master/LICENSE.txt) limits materials to noncommercial use. Not integrated |
| [ROMP / BEV / TRACE](https://github.com/Arthur151/ROMP) | ROMP/BEV recover multiple bodies; TRACE adds temporal tracks/global trajectories; ONNX support exists for parts of the stack | Candidate for a GPU class-motion experiment, not proof of tracking through occlusion. Not benchmarked here; minimum VRAM and frame rate remain unknown. Code [Apache-2.0](https://raw.githubusercontent.com/Arthur151/ROMP/master/LICENSE.md) does not remove body-model obligations |
| [4D-Humans / HMR2](https://github.com/shubham-goel/4D-Humans) | Detector plus per-person transformer mesh recovery with tracking integration | Potential identity/pose improvement in video; larger dependency/runtime stack and no local GPU benchmark. Code is [MIT](https://raw.githubusercontent.com/shubham-goel/4D-Humans/main/LICENSE.md); official setup separately requires registered SMPL assets. A plausible mesh does not establish visible anatomy |
| [MotionBERT](https://github.com/Walter0807/MotionBERT) | Temporal motion representation and 2D-to-3D pose estimation; needs correctly associated tracks and joint conventions | Temporal context may reduce jitter, but a lift of a hallucinated 2D track can remain wrong. Not integrated without floor/inversion and identity-ground-truth evaluation. Code [Apache-2.0](https://github.com/Walter0807/MotionBERT/blob/main/LICENSE); check each checkpoint/training dataset separately |

[SMPL-X model terms](https://smpl-x.is.tue.mpg.de/modellicense.html) distinguish noncommercial research use from commercial licensing. An application's permissively licensed Python code is not a blanket license for its model assets. No SMPL, SMPL-X, SAM or Multi-HMR weights are redistributed in the source package.

For every candidate, front/side/back availability must be tested separately. A side view can support projected flexion yet hide the opposite limb. A back view can remove facial orientation cues. Oblique cameras mix planes, and wide-angle distortion changes straight-line geometry. None of the reviewed models eliminates those problems. Calibrated multiview capture or a depth sensor is preferable when metric 3D measurements are required; a learned monocular depth map alone does not supply measured skeletal depth.

## Hugging Face datasets and action models

Hugging Face was searched for yoga, Pilates, exercise, human motion, 3D pose and mesh assets. Downloaded **AtomicLion1/yoga-poses-dataset** (~157 MB, 1,080 rows) and inspected image samples. Its five coarse pose categories contain photographs, diagrams, watermarks, montage images and duplicates. Selected photographs serve as exploratory visual cases only. Its missing/unclear dataset license and source lineage make it unsuitable as an assumed commercially cleared training set. [Dataset](https://huggingface.co/datasets/AtomicLion1/yoga-poses-dataset).

The reviewed [helloko/yoga_poses](https://huggingface.co/datasets/helloko/yoga_poses) content is pose-description/illustration-oriented, not a measured biomechanics dataset. Pilates-tagged datasets such as [Mazelone/sports_pilates](https://huggingface.co/datasets/Mazelone/sports_pilates) and [lia-prop13/pilates-dataset](https://huggingface.co/datasets/lia-prop13/pilates-dataset) need provenance, subject diversity, camera coverage and labeling audits before training. A repository's license tag does not establish rights to every contained image.

[Yoga-82](https://arxiv.org/abs/2004.10362), [3D-Yoga](https://openaccess.thecvf.com/content/ACCV2022/papers/Li_3D-Yoga_A_3D_Yoga_Dataset_for_Visual-based_Hierarchical_Sports_Action_ACCV_2022_paper.pdf), [3DYoga90](https://arxiv.org/abs/2310.10131) and [Fit3D](https://mihaifieraru.github.io/publication/fieraru_2021_cvpr/Fieraru_2021_CVPR.pdf) are more relevant upstream starting points for pose/action and exercise evaluation. HF mirrors of Fit3D or Human3.6M must not be treated as replacements for upstream access terms. Recognition labels alone cannot validate movement quality, clinical ROM or a posture score.

No exercise classifier was integrated: generic pose-classification checkpoints or action encoders would add a confident exercise name without validating that movement's geometry. The MVP records an explicit user-declared movement protocol and computes only visible projected signals. A next dataset should pair raw consented class video with person identities, visible/occluded joint labels, exercise phase, camera calibration and instructor-reviewed repeatability measurements.
